01 The premise

A course, disguised as an expedition.

Dilli Khoj teaches a full introductory PostgreSQL curriculum as a game. Each ruin guards a sealed archive; reading it means writing the SQL the archive asks for. Get it right and the ruin wakes, unlocking the next. The curriculum is the map.

  • Twenty authored questions, one per ruin, in a fixed teaching order from schema-reading to multi-table joins.
  • Sign in with any Google account. Sign-in is required to play — it saves your progress and identifies you on the leaderboard.
  • Every query is real PostgreSQL — read-only, run against a live database, graded on the server.

02 The player path

From gate to graded solve.

The flow is linear and gated: intro briefing → sign in → walk the ruin → open the archive → Run freely, then Submit. A passing Submit restores the ruin and unlocks the next. Cleared ruins stay open forever for revisiting.

03 The interface

A walkable world beside a working SQL console.

  • Left: a third-person, explorable ruin built in Three.js — dusk lighting, guide arrows to the nearest archive, ambient audio.
  • Right: the archive terminal — the question, a sample output, the schema, and an editor with Run (free practice) and Submit (server-graded).
  • Always visible: XP balance, ruins-restored count, world map, and the mission card.

04 Anatomy of a question

Story, shape, and a live schema.

Every archive follows one structure so students always know where to look:

  • Task with a short story — the in-world objective and the exact rows and columns to return.
  • Sample output — fictional rows showing the answer's shape, flagged order-matters or any-order.
  • Schema with sample rows — each table's columns and a few illustrative rows, so the source data is never a mystery.
  • Hints for XP, then a full solution reveal — both paid for, the reveal gated behind opening every hint.

05 The curriculum, as a city

20 ruins → 8 modules → 7 districts.

Ruins unlock in one fixed order. Contiguous runs of ruins form seven districts, each holding one band of the DBMS syllabus. The order is the single source of truth — progression, unlocks and the leaderboard all read it.

06 The difficulty ramp

Every ruin raises the bar.

Difficulty is encoded by module and district — and by the hint budget: ruins 1–10 get one hint, 11–20 get two. A single walk climbs from filtering catalog rows to windowed analytics and joins with set operations.

07 The XP economy

Help costs; solving never does.

A wrong Submit is free, so students submit fearlessly. Solving is always available. But help must be paid for — and a reveal is a scoring dead end.

  • A reveal awards no XP for the solve that follows — you can't reveal your way up the leaderboard.
  • A no-help player tops out at 500 XP (100 start + 20 solves × 20). Only players who clear all twenty appear on the leaderboard.

08 Grading & fair play

The server is the referee.

  • Server-authoritative judge. Submit calls a Supabase Edge Function that runs the query on real PostgreSQL under a restricted identity — never the browser.
  • Hidden fixtures. Each ruin is graded against a visible case plus hidden datasets, compared order-sensitive or order-free per question.
  • Read-only by construction. Only SELECT / WITH … SELECT, one statement, a 10 KB cap, a statement timeout and a max-rows ceiling.
  • Pinned datasets. Every submission carries a dataset_version so grading is reproducible.

09 Architecture

One SPA, two databases, one referee.

The browser talks to Cloudflare for the app, to Supabase Auth to sign in, and to Supabase RPCs for progress. A Submit goes to the judge-query Edge Function, which runs the query under an executor role against fixture data and writes the verdict under a separate progress role.

10 Auth & security

One source of truth for who's in.

  • Google OAuth with PKCE — the app never sees a password; sign-in happens on Google.
  • Any Google account may play, enforced by a before-user-created hook. Admin identity is separate: the allowlist in game_private.admin_emails is the single server-side source of truth.
  • Admin status is server-computed and returned by game_state(); the client never asserts it.
  • Admin reads are gated and audited — require_admin() guards every privileged RPC and logs it.
  • Solutions never ship to students — the authoring studio is a dev-only bundle, absent from production.

11 Maps, admin & practice

See the city; revisit any ruin.

  • World map. Players reveal only the ruin parcels they've cleared; admins inspect all twenty in the Question Studio.
  • Revisits. Every ruin has two alternate variants — 40 in total — for non-scoring practice that changes no XP, time or unlocks.
  • Leaderboard. Completers ranked by XP, then fastest completion.

12 Compliance & consent

Ready for the OAuth consent screen.

  • Privacy policy & terms of service served from the app's own domain, matching the game's identity.
  • They cover the data actually collected — Google email, name, picture, id — the scopes requested (openid email profile), storage, retention and rights.
  • Both carry the fiction disclaimer and the Developed by Vishnu Gandarapu credit.

13 Deployment

Two platforms, one command.

  • Front end: pnpm build && wrangler deploy ships the SPA to Cloudflare Workers with single-page-app fallback.
  • Back end: Supabase project — SQL migrations, the signup hook, RLS policies, RPCs, and the judge-query Edge Function with its executor / progress database roles.
  • Content pipeline: practice fixtures and expected rows are generated by running the canonical solutions through PostgreSQL — expected output is computed, never hand-written.

14 Status & what's next

Live, and honest about what's next.

All twenty ruins are deployed and graded end-to-end on Cloudflare and Supabase, and sign-in is open to any Google account. The judge accepts the canonical solutions for all 20 with 3/3 cases. The remaining work is depth and durability, not first launch — stronger hidden fixtures and a blind human review across every question and revisit.

  1. Deepen review of all 20 questions and their 40 revisits.
  2. Strengthen hidden fixtures and genuinely different accepted solutions.
  3. Harden expensive-query limits, queues and retries.
  4. Test sustained mixed-question performance; improve polling and rendering.
  5. Add abuse guardrails — CAPTCHA and rate limits now that signup is open.
  6. Widen browser and hardware compatibility testing.
  7. Maintain retention, monitoring and rollback.
